# Aerix — манифест и технический контекст

**Aerix. Effortlessly modern.**

Этот документ вводит нового участника в проект. Для правил работы читайте также
`Project_manual.md` и `Project_rules.md`; для конкретной задачи обязательно
сверяйте актуальный код и остальные документы в `Agent-instructions/`. Описание
состояния ниже — снимок на 7 ноября 2026 года, а не гарантия будущего состояния.

## Что мы создаём

Aerix — лёгкое, простое и современное окружение рабочего стола Linux, которое
должно работать из коробки и со временем стать доступным не только автору.
**Настройка — возможность, а не необходимость.** Цель — цельный пользовательский
опыт: согласованные приложения, удобная навигация, отзывчивый интерфейс и
понятные исходные настройки, а не просто коллекция dotfiles.

Лёгкость означает разумное использование CPU, GPU и памяти, быстрый отклик,
отсутствие лишней визуальной и технической сложности. Она не означает отказ
от Qt или ухудшение UX ради нескольких мегабайт. Современность означает
Wayland-first и осмысленное применение новых инструментов, а не погоню за
новизной. Эксперименты допустимы, но не следует выдавать их за стабильный релиз.

Прежде чем разрабатывать крупную подсистему, исследуйте существующие решения,
включая небольшие проекты: сравните UX, совместимость, лицензию, безопасность,
поддержку, зависимости и стоимость интеграции. Предпочтение готовому решению
не догма: собственная реализация оправданна, если даёт ценность Aerix. Не
добавляйте зависимости или фоновые службы без реальной необходимости.

Автор и агент — технические партнёры. Аргументируйте выбор, честно называйте
риски и предлагайте альтернативы. Общение — на русском, технические термины
можно оставлять на английском. Автор изучает Rust и хочет понимать существенные
решения и команды; глубину объяснений подбирайте по запросу, не превращая
каждую мелочь в урок. Не заставляйте его повторять уже известный контекст.

## Стек и границы текущего репозитория

- Текущая среда разработки: Arch Linux, Wayland, Hyprland, Quickshell/QML/Qt
  Quick; пользователь работает также с Fish. Проверяйте версии и API по месту.
- Этот репозиторий — **конфигурация Aerix Shell**, а не весь будущий DE.
  Соседняя `~/.config/hypr` — локальная конфигурация композитора, не часть этого
  Git-репозитория. Другие приложения и локальные пути не являются обязательным
  стеком для всех пользователей.
- Собственные виджеты создаются в Quickshell. Планируется Theme Engine на Rust:
  единая тема и шаблоны/адаптеры для приложений. Это направление, **не готовая
  реализация в данном репозитории**. Формат данных, интерфейс и IPC не выбраны.
  Собственные Rust-сервисы оправданны лишь при реальной необходимости.
- Установка, упаковка, лицензия, поддерживаемые версии и дистрибутивы,
  окончательный набор функций и формат общей конфигурации не утверждены.
  Не обещайте совместимость или выпуск без реальной проверки.

В перспективе Aerix может объединять композитор, Shell, систему тем, готовые
приложения и службы через Wayland, Hyprland IPC, desktop entries, XDG и другие
подходящие открытые интерфейсы. Не создавайте пустые каталоги и абстракции под
гипотетическую архитектуру. Уважайте пользовательские конфиги; для будущего
Theme Engine заранее обсудите безопасное применение, проверку и откат.

## Целевая архитектура Aerix

Aerix — составное окружение рабочего стола, а не один процесс и не попытка
заново написать системные компоненты Linux. Его задача — объединить их в
согласованный, надёжный и понятный продукт. Схема ниже — **направление развития**:
кроме отдельно отмеченного текущего Shell эти подсистемы пока не реализованы и
не являются утверждённым списком обязательных пакетов.

```text
Пользовательский опыт Aerix
  Bar · Dock · Launcher · Notifications · OSD · Quick Settings · Settings
                              │
Aerix Shell — Quickshell / QML / Qt Quick
  визуальные компоненты · состояние интерфейса · анимации · ввод · popup
                              │
Адаптеры и общие источники данных
  нативные API Quickshell · Hyprland IPC · D-Bus · Wayland · XDG
                 ┌────────────┴─────────────┐
                 │                          │
        Theme Engine на Rust      Rust-сервисы и утилиты при необходимости
                 │                          │
                 └────────────┬─────────────┘
                              │
Системная инфраструктура и готовые приложения
  Hyprland · PipeWire · NetworkManager · BlueZ · UPower · portals · polkit · …
```

### Ответственность слоёв

- **Hyprland** — Wayland-композитор и менеджер окон: фокус, расположение и
  состояние окон, workspaces, мониторы, keybindings, правила и эффекты. Это
  источник данных о своём состоянии; не поддерживайте конкурирующую копию в
  отдельном сервисе без необходимости. Контракты Shell учитывают Hyprland IPC.
- **Quickshell** — визуальный слой Aerix: окна, виджеты, popup, ввод, анимации
  и состояние интерфейса. QML-singleton может быть тонким адаптером системного
  источника, но UI не должен превращаться в набор постоянно выполняемых команд
  или содержать сложную системную бизнес-логику.
- **Rust** — Theme Engine и собственные системные утилиты или сервисы, когда
  для них есть обоснование. Наличие виджета само по себе не требует daemon.
  Rust не заменяет визуальный слой Quickshell.
- **Существующие службы** отвечают за аудио, сеть и прочие системные функции.
  Aerix обращается к ним через подходящие нативные API и открытые протоколы, а
  не переписывает PipeWire, NetworkManager или BlueZ.

Один процесс Quickshell обслуживает Shell: визуальные окна могут создаваться на
каждом мониторе, но одно системное состояние имеет один общий источник. Тяжёлые
редко используемые интерфейсы загружаются по необходимости; фоновые подписки и
процессы имеют понятный жизненный цикл. Ни предполагаемая структура репозитория,
ни отдельный универсальный `AerixService` не должны создаваться заранее.

### Когда нужен собственный Rust-сервис

Сначала проверьте возможности Quickshell, системного D-Bus API и существующих
программ. Небольшого QML-адаптера может быть достаточно. Rust оправдан, когда,
например, сложная логика нужна нескольким клиентам, требуется надёжное
долговременное состояние, нет подходящего интерфейса, нужны парсинг и валидация
конфигурации, безопасная запись и откат или независимые тесты бизнес-логики.

Выбирайте между библиотекой, CLI и долгоживущим сервисом по задаче: daemon
нужен только при необходимости постоянной работы или подписок. IPC, схема
конфигурации, запуск и обработка ошибок выбираются для конкретного случая;
`systemd --user` — возможный механизм lifecycle, но не принятое требование для
всех платформ. Избегайте отдельных демонов для каждого виджета.

### Theme Engine — собственное направление

Планируется Rust-подсистема, которая позволит задать тему один раз и применять
согласованное оформление к Shell и поддерживаемым сторонним приложениям.
Предварительная модель работы:

```text
тема → семантические токены → адаптеры/шаблоны → проверка
     → предварительный просмотр изменений → применение → reload компонентов
```

Токены вроде `background`, `surface`, `textPrimary`, `accent` и `outline` —
примеры для обсуждения, не утверждённая схема. Адаптеры должны учитывать реальные
форматы и механизмы reload, а отсутствие необязательного приложения не должно
ломать Shell. При проектировании обсудить dry-run, валидацию, атомарную запись,
резервные копии, откат и защиту пользовательских конфигов; по возможности
генерировать отдельные подключаемые фрагменты. Формат темы, API, перечень
адаптеров и необходимость daemon или событийного IPC пока не решены.

## Интеграции: Hyprland ecosystem и системные службы

Ниже — архитектурные кандидаты, **не утверждённый список установленных или
обязательных пакетов**. Перед внедрением проверить актуальные версии, доступные
API, совместимость, безопасность, лицензию и альтернативы. Автозапуск,
упаковка, fallback и обработка отсутствующих компонентов требуют отдельного
решения. Локальная конфигурация автора описана ниже отдельно.

| Область | Кандидат и роль | Граница ответственности Aerix |
| --- | --- | --- |
| Окна и workspaces | Hyprland IPC и Quickshell Hyprland API | Получать состояние и отправлять команды; не опрашивать `hyprctl` таймером. |
| Portals | `xdg-desktop-portal`, `xdg-desktop-portal-hyprland`, при необходимости совместимый fallback backend | Screen sharing, screenshot и системные диалоги через portal; выбор backend зависит от интерфейса и конфигурации. Проверять реальные возможности и версию. |
| Idle и блокировка | `hypridle`, `hyprlock` | Существующие механизмы idle/lock; при необходимости интегрировать оформление и настройки, а не писать свой lock screen. |
| Авторизация | `hyprpolkitagent` или другой polkit agent | Графический запрос полномочий; ни Shell, ни Rust-сервис не должны незаметно использовать `sudo`. |
| Обои | Текущий `awww`; альтернатива — `hyprpaper` | Выбрать основной backend; обобщать адаптеры только при появлении реальной потребности во втором. |
| Ночной режим | `hyprsunset` | Возможный backend управления цветовой температурой для Quick Settings. |
| Выбор цвета | `hyprpicker` | Возможный инструмент для настройки темы; интеграция с Theme Engine не реализована. |
| Скриншоты | Текущий HyprCapture; альтернативы — `hyprshot`, `grim`/`slurp` | Сравнить зрелость, совместимость и UX; собственный backend заранее не нужен. |
| Курсоры | Hyprcursor и совместимые cursor themes | Согласованное оформление; поддержку конкретных приложений и fallback проверять на практике. |
| Плагины | HyprGlass и другие плагины | Опциональные улучшения; базовый Shell должен сохранять читаемость и работоспособность без них. |

Portals требуют корректного выбора backend для каждой поддерживаемой функции:
не следует предполагать, что Hyprland backend один покрывает все диалоги или
что fallback автоматически настроен. Проверять screen sharing, file chooser и
работу sandboxed-приложений в реальной сессии. Плагины композитора также могут
зависеть от версий Hyprland и влиять на производительность GPU.

| Системная функция | Источник / кандидат | Возможное использование в Aerix |
| --- | --- | --- |
| Аудио | PipeWire / WirePlumber, нативный API Quickshell или другой подходящий интерфейс | Громкость, mute, устройства и OSD; разовые команды возможны, постоянный polling процессов нежелателен. |
| Сеть | NetworkManager / D-Bus | Состояние и управление соединениями, Wi-Fi, при необходимости VPN. |
| Bluetooth | BlueZ / D-Bus | Состояние адаптера и список устройств; подробный UI загружать по необходимости. |
| Питание | UPower; опционально power-profiles-daemon | Батарея, зарядка, уведомления, профили питания при наличии поддержки. |
| Медиа | MPRIS / D-Bus | Общий источник данных для панели, OSD и управления проигрывателем. |
| Приложения | XDG desktop entries и Quickshell DesktopEntries | Поиск приложений, запуск и иконки; учитывать отсутствие и нестандартные записи. |
| Уведомления | Freedesktop notifications / D-Bus | Выбрать между собственным интерфейсом/сервером на Quickshell и готовым daemon; одновременно конкурирующие notification servers недопустимы. |

Для уведомлений собственный popup и центр могут лучше соответствовать стилю
Aerix, но потребуют ответственности за протокол, действия и ограниченную
историю. Готовый daemon проще сопровождать, однако его интеграция может
ограничивать UX. Решение и возможности установленной версии Quickshell сначала
нужно изучить; наличие уведомлений в схеме не означает их реализацию.

## Направления развития интерфейса

Текущие Bar, Dock и preview — только начало. Возможные следующие вертикальные
срезы: launcher и уведомления; OSD громкости и яркости; состояние питания и
медиа; затем Quick Settings для аудио, сети, Bluetooth, яркости и ночного
режима. Позже интерфейс настроек может управлять темой, анимациями, Dock,
мониторами и сочетаниями клавиш через согласованную модель конфигурации, а не
непосредственным редактированием QML.

Это не обязательная последовательность и не утверждённый MVP. Для каждого
среза сначала выбрать готовый backend или собственную реализацию, определить
поведение при отсутствии зависимостей и проверить завершённый пользовательский
сценарий. Сначала стабилизировать существующий Shell и его интеграции; Theme
Engine, упаковку и новые интерфейсы планировать по приоритетам пользователя.

### Открытые архитектурные решения

- Основной wallpaper и screenshot backend; граница поддержки альтернатив.
- Собственный notification server и launcher или интеграция готовых решений.
- Политика опциональных плагинов, в частности HyprGlass, и fallback без них.
- Формат и интерфейс Theme Engine; нужен ли ему долгоживущий сервис и какой IPC.
- Граница между конфигурацией Aerix и пользовательским Hyprland, а также модель
  установки, обновления и безопасного изменения пользовательских настроек.
- Поддержка других композиторов и дистрибутивов: сейчас основа — Hyprland на
  Wayland; переносимость не обещана без проектирования и реальных тестов.

## Что действительно есть в Shell

`shell.qml` — единая точка композиции. Четыре `Variants` создают на каждом
экране отдельные видимые поверхности и input-прозрачные поверхности теней для
StatusBar и Dock; singleton-сервисы общие для всех экранов.
Подключение и отключение экранов предусмотрено моделью `Quickshell.screens`, но
полноценную проверку hotplug и разных DPI нельзя считать подтверждённой.

```text
shell.qml
├── bar/StatusBarShadow.qml → core/PanelShadow.qml
├── bar/StatusBar.qml
│   ├── ClockWidget.qml → services/ClockService.qml
│   └── KeyboardLayoutWidget.qml
│       ├── services/KeyboardLayoutService.qml
│       └── KeyboardLayoutPopup.qml (LazyLoader, Overlay + HyprlandFocusGrab)
│           └── core/PanelShadowWindow.qml → core/PanelShadow.qml
├── dock/DockShadow.qml → DockLayout.qml → core/PanelShadow.qml
└── dock/DockPanel.qml → DockLayout.qml → DockGroup.qml → DockIcon.qml
    ├── WorkspaceIndicator.qml
    └── WindowPreview.qml (LazyLoader)
services/  DockService, DockPresentation, IconService, ClockService — общие singleton
core/      Metrics, Motion, StandardAnimation, PanelShadow
```

`core/qmldir` и `services/qmldir` регистрируют соответствующие типы и
singleton. Новые системные источники данных размещайте в `services/`, виджеты
панели — в `bar/`; не переносите всю логику в `shell.qml`.

### Dock

Dock показывает **открытые окна**, сгруппированные по workspace, на своём
мониторе. `DockService` читает `Hyprland.toplevels.values`, группирует окна
через `Map` и сортирует группы по ID workspace. Если монитор окна не определён,
фильтр не исключает его: не считать поведение в этом случае доказанной строгой
изоляцией мониторов. Фокус: `toplevel.wayland.activate()` при наличии handle,
иначе проверенный адрес и IPC-команда с учётом `Hyprland.usingLua`.
Переключение колёсиком выбирает соседний существующий workspace монитора;
при достижении края индикатор покачивается.

`DockPanel.qml` управляет выездом, маской ввода, геометрией и событиями;
скрытая панель оставляет узкую полосу активации у нижнего края. Область ввода
не должна перехватывать чужие окна. Взаимодействие с иконками включается после
выезда; hover восстанавливается, если курсор уже находится на иконке. При клике
на окно другого workspace есть задержка закрытия. Ширина ограничена **75 %**
логической ширины экрана; иконки уплотняются, при переполнении предусмотрен
горизонтальный `Flickable` (вертикальное колесо переключает workspace).
`DockPresentation` синхронизирует открытие и итоговую ширину с `DockShadow`,
поэтому тень следует за той же анимацией, но не перехватывает ввод.

`DockGroup` рассчитывает отступы и раздвижение слотов; `DockIcon` отображает
изображение и посылает события, а `WorkspaceIndicator` анимирует обводку
активной группы. Не путайте текущую обводку с историческим предложением о
вертикальных разделителях. Иконки используют исходное изображение, а не
принудительную круглую обрезку; видимый fallback — цветной блок с буквой.
`IconService` ищет desktop entry, затем иконку по app-id/class, имеет общий
ограниченный кэш и сбрасывает его при изменении списка приложений.

`WindowPreview` создаётся через `LazyLoader` при наведении. `ScreencopyView`
получает один кадр, затем live-захват выключается; карточка привязана к окну
панели и позиции иконки. Поведение захвата и позиционирования нужно проверять
в настоящей Wayland-сессии, особенно при удалении окна и смене делегата.
Закреплённые приложения и запуск приложений из Dock не реализованы; политика
special workspaces, fullscreen и недоступных мониторов требует обсуждения.

### Верхняя панель и общий стиль

`StatusBar` постоянно закреплена сверху, резервирует рабочую область через
`exclusiveZone: Metrics.statusBarHeight`, содержит только центральные часы `HH:mm`. Общий
`ClockService` использует `SystemClock.Minutes`. При hover панель запрашивает
`WlrKeyboardFocus.Exclusive`, после ухода — `None`: это осознанное поведение,
влияющее на фокус приложений. Подробности — `Status_bar.md`; его исторические
измерения и значения следует сверять с кодом: например, в текущем `Metrics`
высота 40, а радиус и цвет тени меняются вместе с пользовательской темой.

Оформление и размеры общих поверхностей задаются преимущественно в
`core/Metrics.qml`, тень — `PanelShadow.qml`. Единая кривая движения:
`cubic-bezier(0.05, 0.9, 0.1, 1.05)`, включая намеренный небольшой overshoot.
В QML это `Motion.standardCurve`: `[0.05, 0.9, 0.1, 1.05, 1, 1]`.
`Motion` хранит длительности, `StandardAnimation` использует общую кривую.
Итоговые палитра, шрифты, логотип и система accessibility ещё не утверждены.

**Обязательные namespace слоёв:** `aerix:dock-panel` и `aerix:status-bar`.
Они важны для интеграции с композитором; не меняйте их без решения пользователя.

## Локальная конфигурация Hyprland

В `~/.config/hypr/hyprland.lua` подключены отдельные Lua-модули конфигурации.
Это контекст текущей машины, а не универсальные defaults Aerix:

- `animations.lua` задаёт ту же bezier-кривую; `general.lua` использует master
  layout, gaps 4/10, рамку 1 и цвета, согласованные с текущими панелями.
  `decorations.lua` задаёт radius 8, тень и отключает штатный blur.
- `monitor.lua` содержит локальный режим 2560×1440@165 и scale 1.25; нельзя
  предполагать эти параметры у других пользователей.
- `hyprland.lua` запускает `hyprpm reload` и подключает конфигурации HyprGlass
  и HyprCapture; `autostart.lua` запускает `awww-daemon`. Наличие настроек не
  доказывает, что плагины или процессы сейчас запущены.
- `plugins/hyprglass.lua` включает эффект для layer surfaces, contour mask,
  live resampling до 60 FPS и правило `hg.layer("*")` с исключением обоев.
  Это существенно для внешнего вида и нагрузки GPU; не дублируйте blur/тени
  вслепую и проверяйте поведение без плагина. Встроенный blur отключён отдельно.
- Горячие клавиши привязаны к личным Ghostty, HyprFM и Zen, а также `wpctl`,
  `brightnessctl`, `playerctl` и HyprCapture. Не делайте их hard dependency
  Shell. Lua-конфигурация и Lua-режим IPC существенны для команд фокусировки.

## Качество и проверка

Один Shell, одно состояние — один источник истины; событийные API лучше
постоянного polling. Редкий тяжёлый UI создаётся по требованию, а не просто
скрывается. Измеряйте idle CPU, RSS/PSS, дочерние процессы, стабильность
памяти и при необходимости GPU; не заявляйте об оптимизации без сравнимых
измерений. Исторические замеры и ограничения находятся в `Perfomance.md`.

При изменениях Dock проверяйте маску ввода, клики и фокус точного окна, hover,
анимации, иконки, превью, пустой список и переполнение. Для панели — резерв
места, фокус, геометрию, часы и multi-monitor. Сверяйте `qs log` и при
необходимости `hyprctl layers -j`; проверяйте установленные API и версии.
`qmllint` может сообщать о проблемах метаданных Quickshell или singleton —
разбирайте предупреждения, а не объявляйте их автоматически безвредными.
Всегда различайте проверку кода, документации и реальное тестирование в сессии.

Не вводите секреты в репозиторий или документацию. Ранее локальный
`.claude/settings.json` с токеном отслеживался Git: игнорирование не удаляет
его из истории; при необходимости отзовите токен и отдельно обсудите очистку
истории. Не публикуйте значение секрета.
