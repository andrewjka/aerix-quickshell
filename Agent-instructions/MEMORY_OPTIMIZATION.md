# Quickshell Memory Optimization Manifest

## 1. Основной принцип

Минимизируй постоянное потребление RAM/VRAM без ухудшения читаемости, стабильности и отзывчивости интерфейса.

**Оптимизируй по измерениям, а не предположениям.** Не вводи кеширование, object pooling или дополнительные сервисы без обоснованной необходимости.

## 2. Жизненный цикл компонентов

- Используй lazy loading для тяжёлых интерфейсов, которые открываются редко: Launcher, Settings, Control Center и подобных.
- Используй `Loader.active` для создания и освобождения компонентов по необходимости.
- Учитывай стоимость повторного создания: часто используемые небольшие компоненты необязательно выгружать.
- Не считай `visible: false` освобождением памяти. Скрытый объект продолжает существовать.
- Предотвращай накопление неиспользуемых объектов, обработчиков и ресурсов.

## 3. Изображения и текстуры

- Для крупных изображений устанавливай разумный `sourceSize`, соответствующий необходимому разрешению.
- Используй `asynchronous: true` для больших локальных изображений, когда допустима отложенная загрузка.
- Избегай загрузки полноразмерных изображений ради маленьких превью.
- Не удерживай изображения скрытых интерфейсов без необходимости.
- Не создавай собственный image cache, если встроенного кеширования Qt достаточно.
- Учитывай, что динамическое изменение `sourceSize` может приводить к повторной загрузке изображения.

## 4. Модели и делегаты

- Для больших прокручиваемых коллекций предпочитай `ListView` вместо `Repeater`, создающего все элементы сразу.
- Рассматривай `reuseItems: true`, если делегаты корректно поддерживают повторное использование.
- Сбрасывай локальное состояние делегатов при повторном использовании.
- Останавливай таймеры и анимации неактивных делегатов.
- Не заменяй небольшие статические списки сложными моделями без реальной пользы.

## 5. Сервисы и фоновые процессы

- Повторно используй существующие общие сервисы вместо создания дублирующих экземпляров.
- Загружай редко используемые тяжёлые сервисы по необходимости, если это не ухудшает отзывчивость.
- Освобождай ресурсы после завершения работы, когда это безопасно.
- Не уничтожай постоянно необходимые сервисы ради незначительной экономии памяти.
- Не создавай глобальные registry или object pool без подтверждённой потребности.

## 6. Таймеры и события

- Останавливай периодические операции, когда их результаты больше не нужны.
- По возможности предпочитай событийное обновление данных постоянному polling.
- Не создавай несколько таймеров для одинакового источника данных.
- Проверяй, не продолжают ли скрытые компоненты выполнять ненужную работу.
- Не отключай фоновые операции, необходимые для корректного состояния системы.

## 7. Измерение и проверка

Перед существенной оптимизацией измерь исходное состояние.

Проверяй:

- RAM/RSS процесса Quickshell.
- Использование VRAM, если оно измеримо.
- Изменение памяти при открытии и закрытии интерфейсов.
- Рост памяти после повторных циклов открытия/закрытия.
- Потребление памяти в idle.
- Регрессии отзывчивости и времени открытия UI.

Для первоначальной диагностики используй `ps`, `top` и доступные инструменты профилирования Qt.

Сравнивай измерения в одинаковых условиях. Не считай высокий RSS сам по себе доказательством утечки памяти.

## 8. Правила работы агента

1. Исследуй только затронутые компоненты и их зависимости, если не запрошен полный аудит.
2. Приоритет — подтверждённые проблемы и дорогостоящие постоянно активные компоненты.
3. Предлагай минимальное изменение с понятной ожидаемой пользой.
4. Не усложняй архитектуру ради гипотетической экономии ресурсов.
5. Не изменяй архитектуру и не добавляй зависимости без согласования.
6. Посторонние проблемы фиксируй в `TECHNICAL_DEBT.md`.
7. Выполняй проверки, соразмерные задаче; не создавай избыточную тестовую инфраструктуру.
8. Если оптимизация ухудшает читаемость или сопровождаемость, аргументируй компромисс.
9. Сохраняй функциональность, визуальное поведение и совместимость с существующими компонентами.

## 9. Критерий завершения

Оптимизация считается завершённой, когда:

- Устранена установленная проблема или проверена соответствующая гипотеза.
- Существующее поведение сохранено.
- Не создана неоправданная архитектурная сложность.
- Выполнены доступные релевантные проверки.
- Измеримый эффект подтверждён данными либо честно отмечен как непроверенный.

**Главное правило: не оптимизируй всё подряд. Устраняй реальную стоимость, сохраняя минимальную сложность системы.**
