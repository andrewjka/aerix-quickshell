# Memory Optimization & Lazy Loading — Quickshell/QML

Краткая методичка для агента, выполняющего рефакторинг. Цель — снизить потребление памяти и стоимость запуска оболочки, сохраняя поведение интерфейса и простоту кода.

## 1. Основной принцип

Не создавать и не удерживать в памяти то, что сейчас не нужно. При этом **скрытый (`visible: false`) объект не равен выгруженному**: он может продолжать занимать память, а его таймеры и обработчики — работать.

Оптимизировать по реальной необходимости: сначала найти затраты, затем сделать минимальное изменение и измерить результат. Не вводить сложную инфраструктуру ради гипотетической экономии.

## 2. Изображения

- Не загружать полноразмерное изображение ради маленькой миниатюры.
- Указывать `sourceSize` по требуемому размеру декодирования; для крупных наборов миниатюр рассмотреть отдельный thumbnail-provider.
- Не держать ненужные изображения загруженными. Если содержимое допустимо выгрузить, очищать `source` или уничтожать компонент через `Loader`.
- Проверять необходимость кэширования: кэш ускоряет повторное использование, но удерживает память.

```qml
Image {
    width: 100
    height: 80
    source: "wallpaper.jpg"
    sourceSize: Qt.size(width, height)
    fillMode: Image.PreserveAspectCrop
}
```

`sourceSize` ограничивает запрашиваемое разрешение, но само по себе **не выгружает** изображение при скрытии.

## 3. Большие списки и делегаты

- Для длинных прокручиваемых списков предпочитать `ListView` вместо `Repeater` внутри `Column`/`Grid`, создающего делегаты для всех элементов.
- `ListView` обычно создаёт элементы в районе видимой области; повторное использование экземпляров зависит от возможностей и настройки конкретного типа/версии Qt.
- При переиспользовании делегата не оставлять состояние предыдущего элемента (выделение, анимации, временные данные).
- Не переводить маленькие фиксированные наборы в `ListView` без оснований.

```qml
ListView {
    model: largeModel
    delegate: ItemDelegate { }
}
```

## 4. Повторное использование компонентов (pooling)

Для объектов, которые **часто и дорого создаются и уничтожаются**, можно хранить небольшой пул: `acquire()` получает свободный экземпляр, `release()` скрывает/сбрасывает и возвращает его, предварительный `warmup()` создаёт ограниченное число объектов.

Важно: пул **ускоряет повторное создание, но удерживает память**. Не применять его для редко используемых попапов, если приоритет — минимальный расход RAM. Ограничивать размер пула, очищать состояние и корректно управлять parent/ownership. Реализовывать только при измеренной пользе.

## 5. Жизненный цикл сервисов

- Сервисы, не нужные при запуске, инициализировать при первом обращении.
- Если сервис больше не используется и его безопасно остановить, отключать подписки, таймеры и процессы, затем освобождать объект.
- Общие постоянно необходимые сервисы создавать один раз и переиспользовать; не дублировать одинаковые подписки в виджетах.
- Перед выгрузкой проверять зависимости: другие компоненты могут продолжать использовать сервис.

Идея реестра: `get(name)` создаёт сервис по запросу, `unload(name)` завершает его работу и удаляет из реестра. Не добавлять реестр, если достаточно существующего механизма управления жизненным циклом.

## 6. Таймеры и фоновая активность

Останавливать периодические задачи, когда их результат не нужен. Для обновления содержимого скрытого попапа часто достаточно привязки:

```qml
Timer {
    interval: 1000
    repeat: true
    running: popup.visible
    onTriggered: refreshData()
}
```

Аналогично проверять фоновые процессы, наблюдатели и подписки. Если данные нужны и в закрытом состоянии, не останавливать их автоматически.

## 7. Ленивая загрузка (`Loader`)

Редко открываемые интерфейсы (настройки, launcher, большие попапы) создавать при первом использовании, а не на старте оболочки.

```qml
Loader {
    id: settingsLoader
    active: false
    source: "SettingsPanel.qml"
}

// При открытии:
settingsLoader.active = true
// Использовать settingsLoader.item только после загрузки.
```

- `active: false` откладывает создание; `active: true` запускает загрузку.
- `active: false` после закрытия может освободить созданный объект. Выбирать между освобождением памяти и сохранением состояния/скоростью повторного открытия.
- Для `sourceComponent` можно использовать заранее определённый `Component`.
- При `asynchronous: true` учитывать `Loader.Loading`, `Loader.Ready`, `Loader.Error`; обращаться к `item` только после готовности.
- На время долгой загрузки отображать простой placeholder/индикатор, если он действительно нужен.

Не откладывать загрузку критичных частей интерфейса, которые должны быть доступны сразу.

## 8. Предварительная загрузка (preloading)

Если задержка первого открытия заметна, допускается подготовка часто используемых компонентов после запуска: очередь компонентов, постепенная загрузка через `Qt.createComponent()`, сохранение готовых определений.

- Разносить загрузку по времени, чтобы не блокировать старт.
- Проверять статус `Component.Ready`/`Component.Error` и при асинхронной загрузке дожидаться готовности.
- Предварительная загрузка **обменивает память и фоновую работу на скорость открытия** — не включать её для всего подряд.
- Учитывать зависимости: нужный сервис должен быть готов раньше зависимого интерфейса.
- Предиктивную загрузку, отдельный менеджер и граф зависимостей вводить только при реальной сложности проекта.

## 9. Измерение эффекта

До и после изменений проверять:

1. RSS процесса Quickshell в одинаковых условиях (запуск, открытие/закрытие панелей, длительная работа).
2. Время запуска и задержку первого/повторного открытия тяжёлых компонентов (`console.time()` / профилировщик QML).
3. Число живых объектов, активные таймеры/подписки и отсутствие ухудшения отзывчивости.

```bash
pgrep -a quickshell
ps -o pid,rss,cmd -p <PID>    # RSS в КиБ
 top -p <PID>
```

Для детального анализа использовать QML Profiler. RSS не показывает отдельно все расходы GPU; потребление видеопамяти при работе с изображениями оценивать отдельно, если это существенно.

Числа экономии, приведённые в учебнике (например, 50–90%), — **иллюстративные сценарии, не обещание результата**. Не фиксировать их как критерий успешности. Время запуска измерять по двум реальным временным точкам, а не просто выводить `Date.now()` в одном обработчике.

## 10. Порядок работы агента

1. Найти фактические источники затрат: изображения, большие списки, заранее созданные окна, сервисы, таймеры.
2. Выбрать самый простой подходящий приём из разделов выше.
3. Сделать минимальный локальный рефакторинг без изменения пользовательского поведения.
4. Проверить загрузку, закрытие, повторное открытие, освобождение ресурсов и зависимости.
5. Сравнить показатели до/после; если выгода не подтверждена или сложность выросла несоразмерно, не сохранять оптимизацию ради самой оптимизации.

**Приоритет:** корректность → простота → измеримая экономия памяти/времени. Pooling, кеш-менеджеры, предиктивная загрузка и сложные графы зависимостей — дополнительные инструменты, а не обязательные элементы архитектуры.
